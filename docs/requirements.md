## 1. 产品定义

一个「内核极薄、能力全靠模块」的 Agent 运行时。core 只负责**连接、路由、循环、密钥、审计**；所有能力（工具、模型、记忆、提示、界面）都是可独立部署、可单独运行的模块，通过加密长连接主动接入，跨机器工作。

**一句话**：core 是插座和配电箱，模块是电器；换电器不用改电路。

## 2. 设计原则（不可妥协）

| # | 原则 | 判据（怎么算做到了） |
|---|---|---|
| P1 | **零硬编码接入** | core 代码里搜不到任何具体模块的 id / 名称 / 路径；删掉所有模块，core 仍能启动 |
| P2 | **运行时可发现** | 新模块接入不需要改代码、不需要重启、不需要改配置后 reload |
| P3 | **模块自足** | 每个模块能脱离 core 单独启动、单独测试 |
| P4 | **全链路密文** | 除握手首帧外，任何 payload 不以明文出现在网络上 |
| P5 | **私钥不出核** | core 私钥只存在于 core 进程内存 + 一个 0600 种子文件；不进日志、不进配置、不进模块 |
| P6 | **失败可退化** | 任一模块崩溃/断连/超时，core 与会话存活，错误可解释 |

## 3. 功能需求

> 编号规则：`FR-<域>.<序>`。带 **[M]** 的是必须项，**[S]** 为应该项，**[C]** 为可选。

### FR-1 内核

- **FR-1.1 [M]** core 只含 8 个组件：传输、加密会话、注册表、路由、Agent 循环、策略、审计、配置页。
- **FR-1.2 [M]** core 不 import 任何模块代码；不出现模块专属字符串常量（配置与数据库除外）。
- **FR-1.3 [M]** 新增/移除模块，core 零代码改动、零重启。
- **FR-1.4 [M]** 内核可空跑：无任何模块时启动成功，对用户请求返回「无可用能力」而非崩溃。

### FR-2 协议

- **FR-2.1 [M]** 传输：WebSocket；消息：JSON-RPC 2.0。
- **FR-2.2 [M]** 首帧携带 `protocol: vade/v1`，版本不匹配立即拒绝并给出可读原因；**禁止降级协商**。
- **FR-2.3 [M]** manifest 自描述能力；**未知字段必须忽略**（前向兼容），未知 `capability` 类型忽略并告警。
- **FR-2.4 [M]** 工具全局 ID 为 `{module_id}/{tool}`，暴露给 LLM 时转 `{ns}__{tool}`（`[a-zA-Z0-9_-]`）。
- **FR-2.5 [M]** 同名工具冲突：默认拒绝后注册者，需显式 `alias` 才允许共存。
- **FR-2.6 [M]** 支持 `module/drain` 优雅下线：停止接新调用，等在途调用结束后断开。
- **FR-2.7 [M]** 第一版**禁止模块反向调用** core 或其他模块的工具（防权限放大）。

### FR-3 传输安全

- **FR-3.1 [M]** **必须启用 TLS（wss）**。证书支持：core 自签（首次启动生成 CA）或用户提供；自签时客户端需固定指纹校验（TOFU）。
- **FR-3.2 [M]** 应用层再做一次加密：Noise 握手（`Noise_IK_25519_ChaChaPoly_BLAKE2s` 常规连接 / `Noise_XXpsk3` 首次配对），载荷 AEAD 为 **ChaCha20-Poly1305**，**密钥不依赖 TLS**（TLS 只防传输层，应用层防中间人与落盘）。由 `snow` 实现，**不自研密码学状态机**。
- **FR-3.3 [M]** 每条消息 AEAD 认证，nonce 由 Noise 传输态维护（96-bit，Noise 规范：前 4B 为 0 + 后 8B 小端计数器）；帧头 `counter` 仅用于**重放检测**，接收端必须显式校验单调递增。**方向隔离靠 Split 出的双向独立密钥**（c2m / m2c），不靠 nonce。计数耗尽即强制重握手。
- **FR-3.4 [M]** 前向保密：每连接新生成 ephemeral X25519；长期 X25519 密钥**只参与认证 DH，不直接加密 payload**（Noise 无签名步骤）。
- **FR-3.5 [M]** 握手 transcript 全量哈希绑定（防中间人替换中间值）——由 Noise 的 `MixHash` 天然满足，无需额外实现。
- **FR-3.6 [S]** 密钥轮换：连接存活超过 24h 或消息量超过阈值，主动 `rekey`（`snow` 的 `TransportState::rekey`）或重握手。

### FR-4 接入信任

- **FR-4.1 [M]** 白名单：`module_id → 公钥指纹`，默认全拒。
- **FR-4.2 [M]** 首次接入需**配对码**（core 生成 6 位、5 分钟有效、一次性），配对后登记模块公钥。
- **FR-4.3 [M]** 双向认证：由 Noise IK 完成——core 用白名单里的模块公钥解 msg1，模块用配对时拿到的 core 公钥验 msg2。**不额外做密码学签名**（X25519 密钥不做签名用途）。
- **FR-4.4 [M]** 吊销：删除指纹后**下一次连接即失败**，已连接会话立即断开；吊销需记审计。
- **FR-4.5 [C]** 支持模块声明所需权限范围（scope），core 记录并按 scope 拒绝越界调用。

### FR-5 模块形态（本次新增重点）

- **FR-5.1 [M]** 每个模块是**独立进程 / 独立目录 / 独立依赖**，不与 core 共享 venv。
- **FR-5.2 [M]** **模块可单独运行**：不连 core 也能启动，自带本地入口（CLI 或本地 HTTP），可独立自测全部能力。
- **FR-5.3 [M]** core 不在线时，模块不得崩溃或阻塞业务；自动重连（指数退避 + 抖动），重连后重新注册。
- **FR-5.4 [M]** 模块语言无关：协议公开，官方提供 Python SDK；其它语言按协议实现即可。
- **FR-5.5 [S]** 模块自注册健康检查端点，供独立运行时的探活。

> 编号规则：AMEND 新增的条款**只能往后排**，不得复用已占用的编号。本节 5.4/5.5 是基线条款，AMEND-06 原拟的三条（5.4/5.5/5.6）与基线撞号，已顺延为 5.7/5.8/5.9（AMEND-11 修正）；FR-2.7 保持「禁止反向调用」，`capabilities.update` 改为 FR-2.13。

### FR-6 能力类型

- **FR-6.1 [M]** 至少支持六类：`tools` / `model` / `memory` / `prompt` / `ui` / `event`。
- **FR-6.2 [M]** **模型也必须可模块化**：core 内置一个 OpenAI 兼容适配器作为默认实现，但接口按「可被 model 模块替换」设计，替换不需改 core。
- **FR-6.3 [M]** 同一时刻允许多个 model 模块注册，由策略选择（默认取 manifest 声明的 `priority`，高者优先）。

### FR-7 人工确认（HITL）

- **FR-7.1 [M]** manifest 中 `risk: high` 的工具调用**必须**经人工确认才能执行。
- **FR-7.2 [M]** 确认请求走统一 `approval` 通道：有 UI 模块则推送到 UI 弹窗；无 UI 时降级到 core 的终端交互。
- **FR-7.3 [M]** 超时**默认拒绝**（默认 60s，可配置）；拒绝原因回传给模型，模型可换方案继续。
- **FR-7.4 [M]** 每次确认/拒绝写审计，含：工具、参数摘要、确认人、决策、耗时。
- **FR-7.5 [S]** 支持「本次会话内同类工具自动放行」，会话结束即失效。

### FR-8 UI 模块化

- **FR-8.1 [M]** 对话界面是 `ui` 类型模块，可整体替换，core 不内置业务 UI。
- **FR-8.2 [M]** UI 模块通过**同一套协议**接入（ws + 加密），不得直连 core 内部接口或读 core 数据库。
- **FR-8.3 [M]** core 需向 UI 模块提供：会话流式输出、工具调用事件、审批请求、模块状态订阅。
- **FR-8.4 [C]** 允许多个 UI 模块同时接入（如 web + 桌面 + 移动），事件广播。

### FR-9 配置页面

- **FR-9.1 [M]** core **内置**一个最小配置页，用于**管理模块**：已配对列表、在线状态、manifest 详情、启用/停用、吊销、生成配对码。
- **FR-9.2 [M]**（**边界已被 AMEND-16 扩为「模块治理 + 技能治理 + 记忆治理」，见 §8.16**）该页面是「全模块化」的**唯一内置例外**，边界严格限定为模块管理，不含对话、不含业务配置。
- **FR-9.3 [M]** 配置页需鉴权（本地 token / 密码），默认只监听 `127.0.0.1`，开放外网需显式配置。
- **FR-9.4 [S]** 页面实时刷新（ws 推送模块上下线），不靠手动刷新。

### FR-10 审计与可观测

- **FR-10.1 [M]** 每条 RPC 记录：时间、module_id、方法、耗时、状态、参数摘要（**密钥与敏感字段脱敏**）。
- **FR-10.2 [M]** 一次用户请求可回放完整调用链（LLM 调用 → 工具调用 → 结果 → 下一轮）。
- **FR-10.3 [S]** 统计 token 与成本，按模块归因。

## 4. 非功能需求

| 编号 | 项 | 指标 |
|---|---|---|
| NFR-1 | 并发连接 | ≥ 50 个模块长连接稳定 |
| NFR-2 | 加密开销 | 单消息加解密 < 2ms（1KB payload，本机） |
| NFR-3 | 握手耗时 | 本机 < 50ms |
| NFR-4 | 断线恢复 | 模块断连后 5s 内自动重连成功 |
| NFR-5 | 故障隔离 | 单模块超时不阻塞其他模块调用（并发执行） |
| NFR-6 | 密钥卫生 | 私钥/会话密钥永不写入日志与磁盘（种子文件除外，0600） |
| NFR-7 | 运行环境 | Python 3.11+，Linux / macOS（Windows 不在 v1 范围） |

## 5. 验收标准（可观测判据）

| # | 判据 | 验证方式 |
|---|---|---|
| AC-1 | 另一台机器起新模块，core 零改动零重启，LLM 立刻可调用其工具 | 两个容器，看工具列表与调用结果 |
| AC-2 | 拔掉模块，相关调用返回可解释错误，core 与会话不崩 | kill 模块后继续对话 |
| AC-3 | 抓包无明文：工具参数关键字在 tcpdump 结果中 0 命中 | `tcpdump` + grep |
| AC-4 | 删除模块公钥指纹后，该模块下次连接被拒 | 吊销后重连 |
| AC-5 | `risk: high` 工具未确认时不执行，超时自动拒绝 | 发一个高危调用，不确认 |
| AC-6 | 模块脱离 core 单独启动并能自测全部能力 | 只起模块进程，跑本地入口 |
| AC-7 | 对话 UI 换成另一个 ui 模块，core 不变 | 切换模块后对话仍可用 |
| AC-8 | 配置页能看到模块上下线、能停用与吊销 | 打开页面操作 |

## 6. 明确不做（v1 范围外）

- 多 Agent 协作、Agent 间 handoff
- 模块市场 / 远程安装 / 自动更新
- 局域网自动发现（mDNS）、零配置组网
- 字段级权限控制、RBAC 角色体系
- Windows 支持、K8s Operator、集群化 core
- 移动端原生 UI

### 8.1 AMEND-01 明细（2026-11-07）

**A1 · 部署单元：裸进程 与 Docker 都支持**

- 每个模块仓库必须同时提供：`python -m <module>`（或等价 CLI）直启 + `Dockerfile`。
- 镜像内**不得**包含 core 私钥、core 配置、模块私钥。
- 注入方式：环境变量 `CORE_URL`（wss）、`MODULE_ID`、`MODULE_KEY_PATH`、`CORE_FINGERPRINT`。
- **容器内生成的模块密钥必须挂载持久卷**，否则重启后指纹变化，被白名单拒绝（这是最容易踩的坑）。
- Docker 网络下 core 需监听 `0.0.0.0`，且 TLS 证书 SAN 必须覆盖容器访问用的主机名，否则 wss 校验失败。
- 新增验收：**AC-9** 同一模块用两种方式启动，工具列表与调用行为一致。

**A2 · 配置页：token 鉴权，全程不出现明文**

修订 **FR-9.3** 为：

1. 首次启动生成 32 字节随机 token，**只在终端打印一次**；磁盘只存 **Argon2id 哈希**，不存明文。
2. token 仅通过 `Authorization: Bearer` 提交；**禁止**放在 URL query（会进日志/Referer）、**禁止**存 localStorage。
3. 必须运行在 TLS 之上（https/wss）；登录成功后换发**短期会话 cookie**：`HttpOnly + Secure + SameSite=Strict`，默认 8 小时过期。
4. 连续失败 5 次锁定 5 分钟；每次登录尝试记审计（IP、时间、结果，不记 token 本身）。
5. 页面与 API 同源，写操作带 CSRF token。

**A3 · UI 模块化冲突：维持 FR-9.2 原判**

- 确认：配置页是 core 唯一内置 UI，边界严格限定为「模块管理」；对话/仪表盘/业务界面一律是 `ui` 模块。
- 无新增条目，状态记为「已确认」。

### 8.2 AMEND-02 明细（2026-11-07）

**A4 · 模块多实例：三种并发模型**

`module_id` 标识**能力**，`instance_id` 标识**具体连接**。manifest 新增 `concurrency` 字段，声明该模块允许多实例的方式：

| 模型 | 语义 | 适用 | 注册行为 |
|---|---|---|---|
| `exclusive` | 一能力一实例 | 记忆存储、模型适配器、审计 sink | 第二实例注册直接拒绝 |
| `pooled` | N 实例无状态，请求分摊 | 工具类模块（搜索、文件、浏览器） | 允许 N 个，core 按最少在途分配 |
| `mirrored` | N 实例，**广播同一事件流** | UI 模块、监控面板 | 允许 N 个，事件同步推送 |

- 修订 **FR-6**：新增 `concurrency` 声明；未声明时默认 `exclusive`（保守）。
- 新增 **FR-6.4 [M]**：`pooled` 模式下 core 必须做最少在途分配，并支持实例故障时摘除。
- 新增 **FR-6.5 [M]**：`mirrored` 模式下的实例不参与负载分担，只接收广播。

**A5 · 会话是单一真相源（多端同步的根本）**

> 关键判断：**多端同步不是"端与端之间同步"，而是"所有端同步到 core"。** 任何把会话状态挂在 UI 端的设计都是错的。

- 新增 **FR-8.5 [M]**：会话状态（消息、工具调用、待确认项）**只存 core**，UI 是只读视图 + 输入通道。
- 新增 RPC：`session/attach{session_id, last_seq}` → 返回 `snapshot{seq, messages[], pending_approvals[]}`；之后走 `session/event{seq, type, payload}` 增量推送。
- 新增 **FR-8.6 [M]**：每会话维护单调递增 `seq`；断线重连按 `last_seq` 补发；replay buffer 保留最近 1000 条或 24 小时（以方案 §2.6 为准，AMEND-11 统一），超出发全量快照。
- 修订 **FR-8.3**：UI 订阅的不只是"工具调用事件"，而是完整会话事件流（含流式 token、状态变更、审批）。
- 新增 **FR-8.7 [M]**：同一会话允许多端同时 attach；任一端 attach/detach 不得影响其他端与本会话执行。

**A6 · 设备身份：原生端与浏览器端用两种鉴权模式**

- 新增 **FR-4.6 [M]**：**每台设备一对独立密钥**（`exclusive` 的模块密钥不适用于设备），支持单设备吊销（手机丢了只吊销手机，不影响电脑）。
- 新增 **FR-4.7 [M]**：配对方式为**扫码**——配置页展示二维码，内含 `core 指纹 + 一次性配对码 + 地址`，设备扫码后生成密钥并登记。
- 新增 **FR-4.8 [M]**：区分两种鉴权模式，协议字段 `auth_mode`：
  - `device_key`：原生客户端（桌面/移动），走完整 Noise 握手，设备长期 X25519 密钥参与认证 DH。
  - `browser_session`：webui，走 TLS + HttpOnly 会话 cookie，**不在浏览器保存长期私钥**。
- 理由：浏览器是XSS 可控环境，把长期私钥放 IndexedDB/localStorage 是**假安全**；宁可承认浏览器端的信任边界止于 TLS，也不要给用户"端到端加密"的错觉。

**A7 · UI 交付形态：三端产物**

- 新增 **FR-8.8 [M]**：UI 模块的交付物是**终端设备安装包**（桌面端 + 移动端）**+ webui**，三端共用同一套协议与业务逻辑，允许不同壳。
- 新增 **FR-8.9 [M]**：webui 由 core 托管静态资源（同源），走 `browser_session` 鉴权。
- 新增 **AC-10**：手机与电脑同时 attach 同一会话，一端发消息，另一端 500ms 内看到。
- 新增 **AC-11**：手机端断网 30s 后恢复，能从 `last_seq` 补齐缺失事件，不出现重复或乱序。

**对已冻结接口的冲击（按 §9 规则 3，须回方案阶段重评）**

| 受影响 | 原设计 | 需改为 |
|---|---|---|
| 注册表 | `module_id` 唯一 | `module_id` + `instance_id` + `concurrency` 模型 |
| 事件通道 | 仅 `tools/call` 请求-响应 | 新增 core→UI 的单向事件流 + `seq` + replay |
| 会话模型 | 隐式存在于 core 内存 | 显式 `session_id` + attach/detach + 快照/增量 |
| 鉴权 | 单一模块密钥 | `device_key` / `browser_session` 双模式 |

**A8 · 多端写入：排队串行**

**A11 · 技术栈：T1 定案（2026-11-07 确认，A9 作废）**

触发原因：A9 选 Flutter 的前提是「一套代码出三端」，但 Flutter 的自绘引擎恰好拿不到 A10 要的两个关键资产：

| 拿不到的资产 | 原因 |
|---|---|
| Miuix 皮肤 | Miuix 是 Compose Multiplatform 组件库（Kotlin），Flutter 侧无法调用任何一行 |
| iOS 26 原生玻璃底栏 | iOS 26 的 `TabView` 用 Xcode 26 重编译即自动变液态玻璃浮岛，属于**系统控件外观**；Flutter 自绘不给系统控件留位，拿不到 |

**事实澄清（修正上一轮判断）**：iOS 侧不需要自绘玻璃，成本几乎为零。

| iOS 版本 | 底栏方案 | 成本 |
|---|---|---|
| iOS 26+ | 系统 `TabView`，重编译即得玻璃浮岛；可选 `.tabBarMinimizeBehavior(.onScrollDown)` 滚动收起、`.tabViewBottomAccessory` 挂底部配件 | 约 0 行 |
| iOS 17–25 | `UnionTabView`（MIT，SPM，`glassEffect` + 自定义 tab item）或 `FabBar`（MIT，玻璃底栏 + 集成 FAB） | 引入依赖 |

**结论（T1）**：Android / Desktop / Web 用 **Compose Multiplatform**，iOS 用 **SwiftUI 原生**。A9（Flutter 一套三端）作废。

- 新增 **FR-8.21 [M]**：iOS 端底栏在 iOS 26+ **必须**使用系统 `TabView`（不自绘玻璃）；iOS 17–25 允许引入 `UnionTabView` 或 `FabBar` 作为降级实现。
- 新增 **FR-8.22 [M]**：三端共享**协议与会话状态机**，不共享渲染层。协议实现只允许存在一份（Rust），详见方案 v1.1 §10。
- 新增 **FR-8.23 [C]**：`glass` 皮肤在 Android 上允许使用 AGSL 着色器实现折射；设备不支持 AGSL（Android 12 及以下）时降级为「模糊 + 描边」，**不得崩溃或白屏**。
- 新增 **AC-14**：iOS 26 真机上底栏表现为系统玻璃浮岛；Android 13+ 上 `glass` 皮肤折射生效、Android 12- 上降级可读。

**A20 · 「编辑」的三层语义（关键边界）**

拓扑必须能编辑，但「编辑」有三种完全不同的含义，混在一起会做出一个假的部署编排器。

| 层 | 操作 | 是否改变运行态 | 持久化 | v1 |
|---|---|---|---|---|
| **L1 布局** | 拖动位置、重命名别名、分组、折叠、缩放 | 否 | core SQLite | 做 |
| **L2 治理** | 启用/停用、吊销、断开重连、覆盖并发模型、查看权限范围、生成配对码 | **是，立即生效** | core + 审计 | 做 |
| **L2.5 邀请位** | 画布上放一个占位节点，生成一次性配对码，模块接入后自动转为实心 | 是（等待态） | core | 做 |
| **L3 编排** | 在画布上「新建一个模块」并由 core 拉起进程 | — | — | **不做** |

- 新增 **FR-9.12 [M]**：L2 操作必须**二次确认 + 记审计**（操作者、目标节点、动作、结果）；吊销与停用为破坏性操作，确认文案必须写明影响（如「该模块 4 个工具将从模型工具表中移除」）。
- 新增 **FR-9.13 [M]**：L2.5 邀请位——占位节点携带 `pair_code` 与二维码；配对成功后**同一节点原地转为实心**，不新增节点（否则画布会越来越乱）。
- 新增 **FR-9.14 [M]**：**明确不做 L3**。core 不启动、不停止模块进程；画布是「已接入模块的镜像 + 治理入口」，不是「部署编排器」。跨机部署仍由用户自己的容器编排负责。
- 新增 **FR-9.15 [S]**：拓扑页仅在桌面浏览器提供完整编辑能力；窄屏（<768px）降级为只读列表——**移动端体验由 `ui` 模块承担，不由配置页承担**。

**A21 · 配置页前端：引入构建步骤，运行时仍然零 Node**

原方案 §7 写「服务端渲染 + 原生 JS，无构建步骤」。拓扑编辑器（拖拽、缩放、框选、连线、属性面板）手写成本与缺陷率都不可接受，因此修订：

- 源码 `admin-ui/src`：React + React Flow（或 Svelte Flow），TypeScript。
- 构建产物 `admin-ui/dist` **提交进仓库**，core 只做静态托管。
- CI 校验：重新构建后 `git diff --exit-code admin-ui/dist`，不一致即失败（防「改了源码忘提交产物」）。
- **运行时依赖不变**：core 部署仍不需要 Node。
- 修订原表「无构建步骤」为「**构建期依赖 Node，运行期不依赖**」。

**验收**

- 新增 **AC-17**：拖动节点改变布局 → 刷新页面保持；两台设备打开配置页布局一致。
- 新增 **AC-18**：`kill -9` 某模块进程 → 拓扑对应连线 1s 内变灰虚线，节点仍显示原地址；重启模块后自动回绿。
- 新增 **AC-19**：扫描 `/admin/api/*` 全部响应体，密钥类字段名（`secret|private|token|psk|password|credential`）与长度 >40 的 base64 串命中数为 **0**。
- 新增 **AC-20**：在拓扑上停用某模块 → 其工具在**下一轮对话**从工具表消失，无需重启 core；重新启用后恢复。

### 8.8 AMEND-08 明细（2026-11-08）

**A22 · 会话存储：做接口，不做模块**

会话是 core 的依赖，不是可挂载能力。做成远程模块会付出四项代价：turn 内 6+ 次写跨进程导致事务边界碎裂；core 启动依赖模块导致故障域倒置；会话明文外泄面扩大；而真正想要的两件事（换库、多 core 共享）用存储接口就能拿到。

- 新增 **FR-1.9 [M]**：`SessionStore` 接口（`append` / `read_since` / `update_turn` / `next_seq`），默认 SQLite 实现，PostgreSQL 实现留接口位。
- 明确：**会话不做成模块**。若将来需要多 core 分担同一批会话，走「core 无状态化 + 外置共享存储」，那是架构变更，不是模块化。

**A23 · 外置知识库：走 MCP，不动 core**

- 新增 **FR-12.1 [M]**：外置知识库以 MCP server 形式挂在 `mcp-bridge` 上游，工具自动进入模型工具表，获得 risk 分级、审计、拓扑可见性。
- 新增 **FR-12.2 [M]**：上游 MCP 的 risk **必须显式映射**（`tool_risk`），不得依赖默认值；映射缺失时按 `high`。
- 明确：M4（`memory`）定位为**过程记忆**（自动写、按会话/agent 分区），知识库是**沉淀结论**（显式写、带 provenance）。v1 **不做**自动 promote，两条不重复存储。

**A24 · 扩展点三层，skill 不含执行通道**

- 新增 **FR-13.1 [M]**：扩展点三层 —— `module`（执行，走协议）/ `prompt 片段`（单模块说明书，随 manifest）/ `skill`（跨模块编排，本地文件）。

- 新增 **FR-13.3 [M]**：skill 采用**渐进式披露** —— 默认只注入 `name/description/when_to_use`，正文在激活后注入，上限 3 个 / 8KB，排序必须确定。

- 新增 **FR-13.5 [M]**：判定「是不是模块」的三条硬标准 —— 有 `module_key`、进注册表、可被其他模块路由。任一不满足即不是模块。

**A25 · bridge 上游按实例拆分**

- 新增 **FR-12.3 [M]**：支持一个上游一个 bridge 实例（`instance_id = mcp-bridge-<server>`），拓扑上各自成节点，健康度与故障互不影响。

### 8.12 AMEND-12 明细（2026-11-08）

> 来源：用户对三处待拍的最终裁定 ——「管理面板是 Vade 自己暴露的，和模块的 app 本来就不应该同源」「配对码中英混合、8 位、用完即失效」「模块与 core 之间是不是端到端加密」。前两条是设计错误，第三条是文档表述不严。

**A42 · 管理面与模块 app 必须不同源（推翻 v1.9 §7.1 的同端口 mount）**

v1.9 把 `/admin`、`/app`、`/ui` 挂在同一个 8443 上，理由只是「少起一个端口」。这个理由是错的：

- `/app` 里跑的是 `ui` **模块**的代码，不是 core 的代码。模块的 XSS 等于「第三方 JS 在管理员已登录的 origin 上执行」，可以直读 `/admin/api/nodes`、发吊销请求；`HttpOnly` 只防读 cookie，不防借用 cookie 发请求；CSRF token 同源一样可读。**同源 + 第三方代码 = 没有任何前端隔离手段可用。**
- 数据面可能为了模块接入开在 `0.0.0.0`；管理面永远只该在本机。绑在同一个 listener 上，等于让数据面把管理面带出去。

具体条款：

- 新增 **FR-9.16 [M]**：管理面**独立监听**（默认 `127.0.0.1:8444`），不与数据面 `:8443` 共用 listener，也不与任何模块 app 同源。三者关系：数据面（wss + `/ui/session` + `/healthz`）/ 管理面（`/admin`、`/admin/api/*`）/ 模块 app（模块自托管）。
- 新增 **FR-9.17 [M]**：管理面**不返回任何 `Access-Control-Allow-*` 响应头**（缺省即防线）；`/admin/api/*` 每请求校验 `Origin` 等于自身 origin（`--admin-origin` 可显式覆盖一个），不匹配返回 `403 ORIGIN_MISMATCH`；并校验 `Sec-Fetch-Site: same-origin`。
- 新增 **FR-9.18 [M]**：管理 cookie 用 `__Host-` 前缀（`__Host-ac_admin`），`Secure; HttpOnly; SameSite=Strict; Path=/`，**不带 `Domain`**；写操作叠加 `X-CSRF-Token` 双提交作为兜底。
- 新增 **FR-9.19 [M]**：管理面响应带 CSP `default-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'`，禁止被 iframe 嵌入。
- 修订 **FR-8.9**：原写「webui 由 core 托管静态资源（同源）」，改为「**由 `ui` 模块自托管**；core 可提供 `--serve-ui <dir>` 的宿主，但**默认关闭**、必须显式开启、且强制独立端口」。
- 修订 **FR-9.3**：默认监听拆成两个独立参数——`--admin-bind` 管管理面、`--bind` 管数据面，互不牵连；`--admin-bind 0.0.0.0` 需二次确认并在启动日志打红字。
- 修订 **FR-8.8**：三端产物不变，但 webui 的**部署单元**从「core 静态目录」改为「独立静态服务或 `ui` 模块自带 serve」。

> 澄清一句，免得被误读成自相矛盾：A2 第 5 条写的「页面与 API 同源」指的是**管理页面与 `/admin/api` 同源**（都在 8444 上），这和「管理面不与模块 app 同源」是两件事。前者必须成立（否则 CSRF 与 cookie 都难做），后者必须不成立（否则模块 XSS 直接打穿管理面）。

**必须一起改的实现细节（否则分离了也白分离）**：

1. **cookie 不区分端口。** 作用域是 `(domain, path)`，不含 port。所以 `127.0.0.1:8080` 的页面照样会带 `127.0.0.1:8444` 的 cookie。「不同端口」不构成隔离，必须靠 `__Host-` + Origin 校验 + **host 分离**：管理面固定 `127.0.0.1:8444`，webui 固定 `localhost:8080`，数据面同时接受这两个 host 名。这样 `ac_admin` 在 `127.0.0.1` 域、`ac_ui` 在 `localhost` 域，host-only cookie 天然不互通。注意对应关系是「admin 单独一个 host，webui 与数据面共用另一个」，不是三个都不同。
2. **`/ui/session` 留在数据面**，因此数据面需要 CORS（仅对 `[server] ui_origins` 精确白名单 + `Allow-Credentials`），管理面则永不需要。
3. **`ac_ui` 的 SameSite 约束**：`localhost:8080 → localhost:8443` 是 same-site（不含端口），`Strict` 仍发送；但 `localhost:8080 → 127.0.0.1:8443` 是 cross-site，`Strict/Lax` 都不发，只能退化成 `None`（等于放弃 CSRF 防护）。因此**约束为 webui 页面与它访问的数据面必须同 host、仅端口不同**，启动时校验 `ui_origins` 的 host ∈ `listen_hosts`，不一致直接拒绝启动。

**A43 · 配对码：8 位中英混合，消费即删（推翻 A41 的「保持 6 位」结论）**

A41 当时的判断是「改 8 位要动 5 处 UI，不值」。这个权衡本身没错，但前提错了：6 位数字只有 `10^6 = 2^20` 的空间，限流只能挡住**在线爆破**，挡不住「码被看到/被念错/被拍照后抢先消费」——真实威胁不是爆破，是窥视。同时 6 位纯数字口述错误率高（`6/9`、`0/O`、`1/7`）。

- 修订 **FR-4.2**：配对码改为 **8 位中英混合 = 2 个汉字 + 6 位 base32**（`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，剔除 `I O 0 1`），显示形如 `青松-A7K2M9`；**180s** 有效；**一次性**。
- 新增 **FR-4.9 [M]**：汉字取自固定 256 字表（代码入库，不用运行时字库）；`normalize()` = `NFKC → 去 - / 空格 / · → 字母段 upper`，**HKDF 与 argon2 哈希都用归一化后的串**；C-01 必须给出归一化与 PSK 派生的测试向量（含全角输入、混合大小写、带分隔符三种）。
- 新增 **FR-4.10 [M]**：一次性判定用 `DELETE ... WHERE code_hash=? AND purpose=?` 的 **`rowcount`**，返回 0 即失败；**禁止「标记 used」**——并发下会被消费两次。
- 新增 **FR-4.11 [M]**：码与 `purpose` 绑定存储，消费时校验；错 5 次作废；每 IP 5 次 / 5 分钟；作废与失败都写审计（不记码本身）。
- **影响面（6 处，比 A41 估的 5 处多一处）**：C2 `identity/pairing.py`、C4 `--pair-code` 与 QR payload、C5a 邀请位弹窗、C5b 二维码卡片、U1 配对页、**R3 安全审查清单**。R3 是 A41 漏掉的——审查项里还写着「6 位」。
- **代价如实记录**：中文需输入法，`LANG=C` 终端会乱码。对策：二维码为主路径；`--print-pair-code` 在非 UTF-8 终端额外输出 ASCII 二维码；`--pair-code` 统一按 UTF-8 解析并归一化。

**A44 · 「端到端加密」必须分段说清，不许笼统回答**

- 新增 **FR-3.7 [M]**：文档、审计字段、拓扑图标三处必须一致地区分四段链路：`core↔模块` ✅ E2E（Noise IK）、`core↔原生端` ✅ E2E、`core↔浏览器` ❌ 止于 TLS、`bridge↔上游 MCP` ❌ 明文。审计里 `e2e=false` 的通道，拓扑上画空心锁。
- 新增 **FR-3.8 [M]**：**明确「E2E 不覆盖静态存储」**——`core.key` 是 0600 明文种子，会话库是明文 SQLite；禁止在 UI/文档/宣传里暗示「落盘加密」。要落盘加密请用全盘加密或 TEE，core 不做假的密钥包裹层。
- 新增 **FR-3.9 [C]**：`bridge` 进程是加密边界的终点——上游 MCP 的内容在 bridge 进程内是明文，只有 bridge→core 这一段进 Noise。知识库接入不得宣称「内容全程加密」。

**验收**

- 新增 **AC-33**：两种攻击场景都要测。① 同 host 跨端口（webui 在 `127.0.0.1:8080`，最危险——cookie 会被浏览器自动带上，只能靠服务端挡）：`curl -H 'Origin: http://127.0.0.1:8080'` 直打管理面 → `403 ORIGIN_MISMATCH`；② 跨 host（webui 在 `localhost:8080`）：控制台 `fetch('https://127.0.0.1:8444/admin/api/nodes',{credentials:'include'})` → 被 CORS 阻断，响应无 `Access-Control-Allow-Origin`。

**A46 · 加密流程与密钥轮换写死（澄清「先非对称后对称」）**

用户的理解方向正确，但「非对称加密」这个说法要精确：**非对称算法不加密数据，只协商出对称密钥**；数据从头到尾只用对称加密。

- 新增 **FR-3.10 [M]**：明确四步时序 —— ① 每连接新生成 ephemeral X25519；② 交换公钥算 `ss = X25519(sk_e, pk_e)`（DH，不是加密）；③ `HKDF-SHA256(ss, transcript)` 派生 `k_c2m` / `k_m2c` 两把方向密钥；④ 之后全部 `ChaCha20-Poly1305(k_方向, Noise 计数器, plaintext)`。**长期私钥只参与认证 DH，不直接加密 payload。**
- 新增 **FR-3.11 [M]**：对称密钥**只在内存**，不落盘、不进日志、不进 core dump（`PR_SET_DUMPABLE=0`）；Rust 侧 `zeroize` on drop。
- 修订 **FR-3.6（rekey 具体化）**：触发条件为「存活 > 24h 或单方向 > 1 GiB 或帧数 > 2^20，先到者」；`type=0x06 rekey` 控制帧**用旧密钥加密**；双方各自 `k = HKDF(k, "rekey")`；`counter` 归零但必须携带 `generation`，形成 `(generation, counter)` 二元组，否则归零会被重放检测误判为回退；rekey 帧解不开**立即断连，不回退旧 key**。
- 新增 **FR-3.12 [M]**：**rekey 不提供新的前向保密**（ephemeral 未变）。要刷新前向保密必须重握手；因此规定「rekey 管单 key 用量，重握手管前向保密刷新，生产建议 24h 重握手一次」。二者都做，不能只做一样。

**验收**

- 新增 **AC-36**（**已被 AMEND-18 修订，见 §8.18 / AC-60**）：远程登录四组 —— 只密码 → **登录成功但只读**（cookie 会话，写操作 `403 READ_ONLY_SESSION`）；只签名 → 失败；密码 + 未登记设备的签名 → 失败；密码 + 已登记设备的签名 → 成功且可写。失败的错误码均为 `AUTH_FAILED`。
- 新增 **AC-37**（**已被 AMEND-14 替换，见 §8.14**）：setup 只从回环可访问，非回环 `403 SETUP_LOCAL_ONLY`；30 分钟未完成 → 管理面拒绝启动；完成后 `POST /admin/setup` 返回 404；`authorized_keys` 为空且 `--admin-bind 0.0.0.0` → 拒绝启动。

**A54 · 技能安装一律进 `pending/`（修订 FR-9.40）**

- 新增 **FR-9.51 [M]**：**安装期不执行任何脚本** —— skill 只有文本与资源文件；zip 里出现可执行文件（`.sh` / `.py` / `.exe` / `package.json` 等）**直接拒绝**（不是忽略）；不存在 `post_install` 钩子。

**A55 · 配置页回到自研 App 内 WebView（修订 FR-9.45/9.46/9.47）**

AMEND-16 把系统浏览器定为主路径，理由是「零代码风险」。这个理由忽略了一件事：**浏览器拿不到第二个因子**，于是「非回环必须双因素」这条在浏览器上根本无法满足，只能退化成「只有密码」。系统浏览器当主路径，等于主路径天生单因子。

用户的判断是对的：**这个管理页只有我们自己的模块能正确承载**——只有自研 App 能调系统安全区拿签名能力、能做证书 pin、能有稳定的设备身份让「双向同意」有意义。所以配置页的主宿主就是 App。

同时要正面回答那个反问：**设备被入侵的话，浏览器不也被入侵吗？** 是，在「设备已失守」这个维度上两者没有本质差别，不能拿「更安全」当 WebView 的理由。WebView 的收益是**能力**（硬件密钥签名）、**可控**（加载什么、连哪里由我们定）、**身份**（稳定设备标识）。这三条浏览器都做不到。

- 修订 **FR-9.45**（覆盖 AMEND-16 版本）：`ui` 模块**内嵌 WebView 打开管理页**，加载**随 App 包分发**的静态资源（`app://admin/` / `file:///android_asset/admin/`）；**禁止** WebView 顶层加载 `https://<core>:8444/admin`。系统浏览器入口保留，但**降为只读**。
- 修订 **FR-9.46**（覆盖 AMEND-16 版本）：**禁止 `ui` 模块以任何形式转发 `/admin/*`** —— HTTP 代理、本地端口映射、改写 `fetch`、`shouldInterceptRequest` 中转，全部禁止。理由在 AMEND-16 基础上加一条：WebView 有了原生桥之后，模块进程能截获的就不只是明文，还包括管理员会话与签名请求。
- 修订 **FR-9.47**（覆盖 AMEND-16 版本）：WebView **安全约束八条**（详见方案 §7.11）—— ① 只加载内置资源；② core 的 `/admin/api/*` 只返回 `application/json` + `nosniff`；③ 桥接白名单三方法（`getDeviceInfo` / `sign` / `secureStore`），禁止反射式接口；④ `sign()` 只接受本 App 生成的 challenge 模板，首次登录必须弹原生确认；⑤ 关闭 `allowFileAccessFromFileURLs` / `allowUniversalAccessFromFileURLs` / 混合内容放行；⑥ 内置页面自带 CSP，页面内禁止 `innerHTML` 插值用户数据；⑦ `onReceivedSslError` 只允许 `cancel()`；⑧ 审批弹窗、密码输入、指纹核对全部用原生 UI，不经 WebView。
- 新增 **FR-9.53 [M]**（**已被 AMEND-18 §8.18/A61 修订**）：**浏览器访问管理面为只读** —— 会话标记 `mode=browser`，**已认证**的非 `GET` 业务请求返回 `403 READ_ONLY_SESSION`；`POST /admin/api/login`、`/login/challenge`、`/logout`、`/token/refresh`、`/admin/setup*`、`/admin/api/health` **豁免**。**回环浏览器同样只读**——权限由凭据类型决定，不由来源决定。前端按只读模式渲染，顶部常驻「只读模式，请用 App 打开以进行配置」。
- 新增 **FR-9.54 [M]**：**管理面会话用 Bearer，不用 cookie** —— access token 15 分钟只存内存，refresh token 30 天存钥匙串（`ThisDeviceOnly`）且每次刷新必须设备签名；每设备 1 个活跃 refresh，新登录踢旧；登出加 `jti` 黑名单。cookie 只用于浏览器只读模式。
- 修订 **FR-9.20**（覆盖 AMEND-13 版本）：**写操作的双因素要求** —— 非回环来源对 `/admin/api/*` 的**非 GET** 请求，必须携带**已绑定设备的挑战签名**，缺一律 `403 READ_ONLY_SESSION`（浏览器就是这种情况，不是拒绝登录，是拒绝写）；回环来源豁免。原「非回环登录一律拒绝」改为「登录允许，写操作拒绝」——因为只读访问本身有价值（临时用别人电脑看一眼状态），而它不构成接管风险。
- 修订 **FR-9.18**（覆盖 AMEND-12 版本；**AMEND-18 再确认**）：`__Host-` cookie 与 `X-CSRF-Token` 双提交，**仅适用于浏览器只读模式**；App 内 WebView 用 `Authorization: Bearer`，不涉及 cookie 与 CSRF。**回环浏览器同样只读**（D76）。

> **关于「Bearer 又回来了」**：AMEND-13 曾写「移除 `Bearer` 方案」（§8.13 接口影响）。当时的选择是 cookie + `__Host-` + CSRF，理由是不让 XSS 读到 token。v1.15 改回 Bearer，理由不是「cookie 不好」，而是**场景变了**：主宿主从系统浏览器变成 App 内 WebView，而 WebView 里的 cookie 要同时处理 `SameSite`、iOS 第三方 cookie 策略、自签证书下 `Secure` 不生效、`__Host-` 前缀限制四件事，每一件都能让登录静默失败。代价是 XSS 能读内存里的 token——用 §7.11 第 6 条（页面内禁止 `innerHTML` 插值）来抵消。两版都有明确理由，不是摇摆；如果将来回到浏览器为主，cookie 那套仍在 §7.1.2 里可用。
- 修订 **FR-9.15**（覆盖 AMEND-07 版本）：原写「窄屏降级为只读列表，移动端体验由 `ui` 模块承担」。现在 `ui` 就是用 WebView 打开**同一份**管理页，所以**窄屏必须能操作**：列表/技能/记忆/设置全部在 375pt 下可用；只允许「拓扑画布」在窄屏降级为节点列表（可视化降级，不是权限降级）。

**A56 · 设备绑定：公钥本地导入 + token + 加密请求（新增 FR-9.55）**

用户的原话是「公钥需要我们自己上传到客户端（不是云端），然后再输入 token，通过公钥加密，才向 core 发送连接请求」。这句话里有两个容易混淆的「公钥」，必须拆开说清：

| 谁的公钥 | 往哪传 | 作用 |
|---|---|---|
| **core 的身份公钥** | 用户**手工**导入 App（扫码 / 粘贴），**不经云端任何中转** | App 用它 pin 住「我要连的是哪台 core」，并算出指纹让用户核对 |
| **设备的公钥** | App 在绑定请求里提交给 core | core 存进设备表，之后登录用它验签 |

所以「用公钥加密再发」指的是：**用 core 的公钥加密请求体**（里面含 token 与设备公钥），到 core 那边用私钥解开。设备自己的密钥是**签名**密钥，不做加密——硬把它当加密密钥是误用，且硬件密钥库通常不允许同一把密钥同时开签名与协商用途。

- 新增 **FR-9.55 [M]**（**已被 AMEND-18 §8.18/A59 修订**）：**设备绑定协议** —— `GET /admin/bind/info`（带绑定票）→ 校验 `fp8` **并验 `hello_sig`（覆盖 `kex_pub`/`challenge`/`ticket_hash`/host）** → `POST /admin/bind`（body `{ticket, eph_pub, nonce, ct}`；`ct` 用临时 X25519 与 core 静态 X25519 派生的 AES-256-GCM 密钥加密，AAD 绑 `fp8 + ticket_hash + challenge + kex_pub`，内含密码、设备公钥、时间戳、签名）→ 返回设备会话。完整序列见方案 §7.12。
- 新增 **FR-9.56 [M]**：**设备密钥规格** —— 主路径 `ECDSA P-256 + SHA-256`，私钥必须进 `Secure Enclave` / `StrongBox` / `TEE` 且不可导出（`hardware_backed=true`）；`Ed25519` 仅用于软件密钥（桌面 CLI、救援），标 `hardware_backed=false` 并在 `/settings` 黄色标注；ECDSA 验签必须拒 `s > n/2`（low-S），防签名可延展破坏一次性语义。
- 设备表落 `data/admin/devices.json`（`0600`），条目 `{device_id, label, alg, pubkey, fp8, hardware_backed, added_at, added_from_ip, last_used_at}`；上限 5 台；吊销立即失效并踢掉该设备换发的所有会话。
- 修订 **FR-9.22**（覆盖 AMEND-16 版本）：设备登记有**三条**路径 —— ① **App 绑定**（主路径，扫码 + 绑定票 + 设备签名，无需电脑）；② 已登录会话内 `POST /admin/api/devices`（**step-up 重输密码**）；③ core 本机 `core admin trust-key`（**救援**，从 `~/.ssh/*.pub` 导入并转成 `devices.json` 条目）。

**A57 · 删除 SSH 主路径（修订 FR-9.45 的相关推论）**

AMEND-16 的「首次跨机访问三条出路」里，两条要求「有一台电脑」；AMEND-13 更直接把 SSH 隧道写成首选。**这些都不成立**：用户在通勤路上、只有手机、容器已经在云上跑着，这是常态，不是边缘情况。

- **SSH 隧道从用户路径删除**，只保留为开发者本机调试手段，且不写进面向用户的 runbook。
- `core admin proxy` 保留，明确标注「给脚本 / CI / 桌面运维」，因为它要求本机能跑 Python 并持有软件密钥。
- 首次配置的完整用户路径改写为：**手机浏览器开 setup 页 → 页面显示二维码与大字指纹 → App 扫码 → 核对指纹 → 设密码 → 完成**（方案 §10.1.1）。四步，全程手机。
- 新增 **FR-9.57 [M]**（**已被 AMEND-18 §8.18/A58 修订**）：**setup 页必须渲染绑定二维码** —— `vade://bind?h=&p=&fp=&tls=&t=`，**只在已解锁（回环或 `POST /admin/setup/unlock` 通过）且仍有有效绑定票时出现**；`t` 是 26 字符一次性 `bind_ticket`，不是 `setup_token`；同时显示大字 `fp8` 供逐字核对；**手输三字段兜底**（扫码失败不能卡死）。

### 8.18 AMEND-18 明细（2026-11-08 · 审查修正）

> 来源：v1.15 发布后的四路独立审查（一致性 / 协议 / 任务拆解 / 需求覆盖）。子代理共报 66 条，逐条回原文核对后**确认 41 条**，其余为重复、误判或文档已写明取舍。本修订**不引入新能力**，只做三件事：封堵两处可被利用的入口、消除自相矛盾、补齐无人承接的交付物。

**A58 · setup 页必须先验 token 再下发二维码（修订 FR-9.25 / FR-9.57）**

v1.15 写「setup 页固定渲染二维码」，且 `GET /admin/setup` 无鉴权。只要 8444 对外，任何打开该页面的人都能拿到 `t=<setup_token>`，然后用自己的设备密钥 `POST /admin/bind` 并在未初始化时**顺手设一个初始密码**——一步接管。这不是「二维码被拍照」的弱风险，是「打开网页就拿到」。

- 修订 **FR-9.25**：非回环来源的 `GET /admin/setup` **只返回** `{setup_required:true, requires_token:true}`，**不含 `bind_url`、`fp8`、token**；新增 `POST /admin/setup/unlock {setup_token}`，验过才返回 `{bind_url, fp8, expires_at}` 并设 10 分钟 `__Host-ac_setup`（HttpOnly、SameSite=Strict、只作用于 setup 路由）。回环直接返回。
- 修订 **FR-9.57**：二维码里的 `t` 是**独立的 `bind_ticket`（16B / 26 字符 / 10 分钟）**，不是 `setup_token`；URI 增加 `tls=<SHA-256(SPKI)[:16]>`。
- 新增 **FR-9.59 [M]**：**setup 解锁态** —— `setup_token` **只出现在 POST body**（`/admin/setup/unlock` 或 `/admin/setup`），禁止 query string 与 header；解锁态 10 分钟（`__Host-ac_setup`）；未解锁访问 setup 路由**不得得到任何票或指纹**。

**A59 · 绑定向导必须整体签名（修订 FR-9.55）**

`fp` 只覆盖 `core_pub`，管不到 `kex_pub` 与 `challenge`。能终止 TLS 的攻击者（恶意反代、LB、被替换的自签证书）可以保留真 `core_pub` 通过指纹校验，同时把 `kex_pub` 换成自己的，于是 App 把密码与票加密给攻击者。只校验 `core_pub` 的信封，等于只防被动抓包。

- 修订 **FR-9.55**：`GET /admin/bind/info` 增加 `hello_sig = Ed25519(core_identity_priv, "vade-bind-hello-v1\n" || kex_pub || challenge || SHA256(ticket) || admin_host)`。App 用已 pin 的 `core_pub` 验签，失败即中止并返回 `BIND_HELLO_SIG_INVALID`。
- 修订 **FR-9.55**：AAD 改为 `"vade-bind-v1" || fp8 || SHA256(ticket) || challenge || kex_pub`；**`ticket` 移到明文字段**——v1.15 把 ticket 放进密文又要求 AAD 含 `ticket_hash`，解密前算不出 AAD，是循环依赖。
- 修订 **FR-9.56**：`hardware_backed` 由设备自述，core 存 `{hardware_backed, attested:false}`，**不得用于授权判断**。

**A60 · 票必须「先验后删」（修订 FR-9.58）**

v1.15 的校验顺序把 `DELETE ... RETURNING` 排在解密与验签之前。拿到票的人（拍照、肩窥、日志）发一个坏密文或错签名就能把票烧掉；重复几次，合法用户在 10 分钟内再也绑不上。这是一个零成本的 onboarding DoS。

- 修订 **FR-9.58**：顺序改为「SELECT 校验存在/未过期/未消费 → 解密与 AAD → 验签 → 吊销表 → 设备数 → 全部通过后在**同一事务**里 `DELETE ... WHERE consumed_at IS NULL` 并检查 `rowcount=1` → 登记设备」。任一失败显式 `ROLLBACK`，**票不消费**。

**A61 · 权限由凭据决定，不由来源决定（修订 FR-9.20 / FR-9.53）**

方案里两张表互相矛盾：§7.1.3 写「回环 = 全功能」，§7.10 写「系统浏览器任意来源 = 只读」；AC-53 也没区分回环。按前者，本机浏览器能写；按后者，不能。开发只能猜。

- 修订 **FR-9.20 / FR-9.53**：**`Authorization: Bearer` 才能写，`__Host-ac_admin` cookie 一律只读——包括回环**。回环只意味着「可以省略设备签名换取 Bearer」，不意味着 cookie 可写。
- 修订 **FR-9.53**：`403 READ_ONLY_SESSION` 只作用于**已认证的 cookie 会话**；`POST /admin/api/login`、`/login/challenge`、`/logout`、`/token/refresh`、`/admin/setup*`、`/admin/api/health` **豁免**（否则浏览器连登录都做不了）。
- 新增 **FR-9.60 [M]**：**refresh token 不出原生层** —— WebView 的 JS 只持有 access token；刷新由原生代发 `POST /admin/api/token/refresh`（签名含 `refresh_jti`）。避免 XSS 读走 refresh 后调 `sign()` 无限续期。
- 新增 **FR-9.61 [M]**：**自签证书的 SPKI pin** —— `vade://bind` 带 `tls` 字段；pin 逐字匹配时把该证书注册为信任锚，**禁止**用 `onReceivedSslError { proceed() }` 放行。可信证书部署不需要此字段。

**A62 · 承接缺口（任务书，不动需求语义）**

#### 8.22.2 修订条款（8 组，逐条标 AMEND-22 修订）

**R1 · FR-8.2（AMEND-22 修订）· 控制面走 ws，附件字节走独立 HTTPS 数据面**

- **修订后**：UI 模块通过**同一套协议**接入（ws + 加密），不得直连 core 内部接口或读 core 数据库。**唯一例外**——附件字节走独立 HTTPS 端点 **`POST /ui/blob`**（设备密钥鉴权、分片、断点续传；浏览器会话可写性随 D100 的凭据规则与 CSRF 防护），**不得进 JSON-RPC 帧**；控制面（会话、事件、审批、状态订阅）仍全部走 ws + 加密。
- **口径**：原文「同一套协议」约束的是**控制面**。数据面允许独立 listener，但必须**同一信任域 + 同一鉴权 + 同一审计**——不是第二套协议栈，也不是第二套鉴权体系。
- **判据**：控制面抓包 0 明文（沿用 AC-3）；上传 8MB 附件时任何 ws 帧 <64KiB（附件字节不在帧内）；无设备密钥打 `POST /ui/blob` → `AUTH_FAILED`；审计里 `ui/blob` 与 `ui/submit` 属同一条可回放链。
- **依赖**：**需 RFC-NNNN（待编号）**· C-05 追加 `POST /ui/blob`（若端点归 core HTTP 层）+ 分片 / 续传 / TTL 语义；与 FR-8.39～8.42 同属 R1 附件与多模态族。

**R2 · FR-8.5（AMEND-22 修订）· 真相只存 core，客户端只持可丢弃派生状态**

- **修订后**：**真相**（会话、消息、turn 状态、审批、审计）**只存 core**；客户端仅持**可丢弃派生状态**——草稿、搜索索引、皮肤偏好，以及附件本地缩略图缓存。派生状态**不参与跨端一致性、不作为真相源、丢失不影响正确性**；core 从不读它。
- **边界**：派生状态可随时清空、无需迁移；**不得**由派生状态反推或修正 core 记录（写路径只经 `ui/submit` 等 RPC）；派生状态不得作为审批、权限、计费的判据。
- **判据**：清空客户端本地数据后重进会话，消息 / turn 状态 / 审批状态 / 审计与清空前逐项一致；A 端草稿在 B 端不可见（FR-8.44 已定 v1 不做跨端草稿）；删除皮肤偏好只回落默认皮肤，会话不受影响。
- **指向**：**FR-8.44**（草稿按 `session_id` 本机保存）、FR-8.27（本地搜索索引，缺 `session/search` 时的降级路径）、FR-8.16 / 8.20 / 8.67（外观偏好本机存储）。
- **依赖**：无（口径澄清，不改协议）。

**R3 · FR-8.26（AMEND-22 修订）· 一级目的地 4 个、手机会话详情、桌面双栏 + 右面板**

- **修订后（补充，不改会话列表的排序 / 分组 / 动词集）**：
  - **一级目的地确认为 4 个**：会话 / 活动 / 能力 / 我的。不设第 5 个（FR-8.77 原约束保留）；"列表 → 详情"两级、时间桶排序与列表项动词集合（置顶 / 重命名 / 归档 / 删除 / 导出 / 标记未读）全部不变。
  - **手机**：进入会话详情后**隐藏底栏**，详情为**全屏页 + 顶栏返回**；输入区、IME 与浮动胶囊（`miuix` + `floating`/`floating+blur`）不得互相叠压（键盘弹起隐藏底栏，与 FR-8.72 一致）。
  - **桌面**：**双栏 = 会话列表 + 详情**，右侧另有**可折叠右面板**（默认收起，`⌘\` / `Ctrl+\` 切换）；**面板样式可自定义**（承载组件、宽度档位可配；样式属本机偏好，D20 同口径）；右面板**可承载模块提供的页面**（见 FR-8.79）。
  - **与 FR-8.76 的关系**：≥1200dp 的"三栏"即**双栏 + 右面板展开态**，不是第三种布局；右面板收起时各断点（<600 / 600–839 / 840–1199 / ≥1200dp）的容器映射不变。
- **判据**：手机详情页底栏不可见，IME 弹起时输入区完整可见、胶囊不遮挡发送按钮；桌面连按 `⌘\` 两次右面板开合且会话滚动位置不变；改右面板样式后重启保持；模块有页面时右面板出现入口、无页面时不出现（FR-8.79）；三端截图对照一级目的地均为 4 个。
- **依赖**：无（客户端容器行为）；右面板承载模块页面的部分依赖 **C-19（待冻结）**。

**R4 · FR-8.43（AMEND-22 修订）· 端上转写定案，桌面无 STT 隐藏麦克风**

- **修订后**：确认 **v1 端上转写**——音频不出设备、core 不存音频、**不引入 `audio/transcribe`**；其余交互不变（按住录音、上滑取消、松手转写、转写文本进输入框**不自动发送**、权限被拒回落键盘且不再重复弹窗）。**补**：桌面端若操作系统无可用 STT（无系统听写 API 或调用不可用），**隐藏麦克风按钮**，以一次性说明解释原因；**不得**显示禁用按钮、**不得**弹错误提示、**不得**因该分支写错误日志。
- **判据**：无 STT 的桌面环境下输入区不出现麦克风按钮，且无 toast / 无 `UNSUPPORTED` 日志；有 STT 的桌面与手机可完成 30s 录音转写，文本可编辑且未自动发送（原判据保留）；抓包确认无音频上行。
- **依赖**：无（端上方案无协议依赖）。若日后改走 core 转写，需 **RFC-NNNN（待编号）· `audio/transcribe` + 音频保留策略**，并同时改本条。

**R5 · FR-8.46～8.50（AMEND-22 修订）· 模型优先、能力过滤、用量两口径、图片只存压缩图**

- **FR-8.46（AMEND-22 修订）**：模型解析顺序定为 **会话级显式选择 > 全局默认 > `manifest.priority`**。`manifest.priority` **只决定默认模型**——FR-6.3 的选择规则收敛为"无显式选择时取 priority 高者"，**不得**覆盖用户在本会话的选择。切换器显示当前**生效来源**（会话 / 全局 / priority）。切换不重建会话、不丢草稿；无 `model/*` RPC 时仍降级为只读徽标，**不得伪造列表**。
- **FR-8.47（AMEND-22 修订）**：模型列表**按能力标签过滤与提示**——切换器顶部提供「视觉 / 工具 / 长上下文（≥128k）」三个过滤项；条目以徽标呈现 `input_modalities`、是否支持工具、`context_window`。**能力未知或缺字段的模型不得入选过滤结果**（只能在全量列表显示为"未知"），不做乐观假设。
- **FR-8.49（AMEND-22 修订）**：用量**两者并存**，同一份 usage 两种视图——①**审计视图**：按模块归因（FR-10.3 的归因口径不变，取 core 审计数据）；②**会话视图**：会话累计与预算（`turn.completed.usage` 累加，input/output 分开，客户端**不自算 tokenizer**）。两个视图**必须可对账**（同一 turn 的 usage 逐项相等）；预算阈值提示与超限阻断由 core 判定，UI 只负责提示与解释。
- **FR-8.50 / FR-8.40（AMEND-22 修订 · 图片存储）**：按 D96，客户端上传前统一压缩为**长边 ≤2048、≤5MB**，**原图不保留**。因此 FR-8.50 第③层"已压缩，**原图可下载**"改为"**已压缩，原图未保留**"；FR-8.40 的"原图 + 派生图两 id"降为**单 `file_id`**（core 只存压缩图）。三层降级结构（选图提示 / `UNSUPPORTED` 错误卡 / 客户端降采样）与"任何一层都不得静默丢图"的约束不变。
- **FR-8.48**：不变（会话级参数覆盖已成立，仅需在"来源"标注中体现"会话覆盖 > 全局 > 默认"）。
- **判据**：会话内选 B（priority 更低）、全局默认 A → 本会话用 B、新建会话用 A；移除全局 A → 新建会话回落到 priority 选中者；"视觉"过滤后纯文本模型不出现；连续 5 轮后审计视图与会话视图的 usage 逐项相等；上传 6000px 图 → core 侧只有 1 个 `file_id`、长边 ≤2048，UI 标注"原图未保留"。
- **依赖**：**需 RFC-NNNN（待编号）· `model/list` + 会话级选择持久化 + 能力元数据 + 会话累计 / 预算 + `file_id` 单一化**（C-05 无 `model/*`；C-18 缺 `llm.model_module`）。

**R6 · FR-8.54 / 8.55（AMEND-22 修订）· 确认新增 `waiting_input`**

- **FR-8.54（AMEND-22 修订）**：ask-user 的阻塞语义与审批**继续分离**，**确认新增 turn 状态 `waiting_input`**（不复用 `waiting_approval`）：输入请求弹出时 turn 进 `waiting_input`，输入区禁用并显示原因；提交 / 取消 / 超时后离开该状态。**契约改动已确认**：C-06 `turn_states` 枚举**需增 `waiting_input`**，连同 `turn.input_required` / `turn.input_resolved`、`turn/input` 与 `turn/input.cancel` 一起走 **RFC-0008**。旧端对未知状态按 `running` 渲染并给降级提示（前向兼容）。
- **FR-8.55（AMEND-22 修订）**：多端一致与审计要求不变；补一条——`waiting_input` 期间**显式只读会话**提交返回 `READ_ONLY_SESSION`，其余端 1 个 RTT 内关闭对话框。
- **判据**：触发 ask-user → 事件流出现 `waiting_input`（旧端渲染为运行中 + 降级提示，不崩、不空转）；提交后 turn 离开该状态且 `turn.input_resolved` 只出现一次；超时后按 core 策略转 `failed`/`canceled`，模型收到 `CANCELED` 而非空值。
- **依赖**：**需 RFC-0008（待起草）**· C-06 枚举 + 事件对；审计字段（请求方、`input_id`、耗时、是否超时）同 FR-8.55。

**R7 · FR-8.63（AMEND-22 修订）· 原生技能页定案，管理面强制 token**

- **修订后**：技能管理**定案为客户端原生技能页**（不是 WebView 页面）；安装与更新**仍复用 FR-9.40 / FR-9.52 的 `preview → pending → approve` 三步**与全部校验规则（zip-slip / SSRF / 大小上限 / 安装期不执行脚本 / 7 天 TTL），**不另起一套**。原生页只调 admin API，不自建第二套权限模型。**配置页（WebView）连 admin 面时强制 token 鉴权**——必须持 **Bearer access token**（D69 口径），**不接受 cookie 会话**；原生技能页与 WebView 配置页**共用同一套 admin API**（C5a 的 `/admin/api/*`），能力集与错误码一致。
- **判据**：原生页安装 `../evil` 的 zip → 与 AC-45 同判据被拒且无越界写入；同一技能在原生页与 WebView 状态一致（approve 后两处都 `active`）；WebView 仅带 cookie 调 `/admin/api/*` 写方法 → `AUTH_FAILED` / `PERMISSION_DENIED`（**不得**静默降级为只读成功）；审计可见同一个 `preview_token` 仅被消费一次。
- **依赖**：无新契约（复用 C5a admin API）；**需 RFC-NNNN（待编号）**定稿"WebView 禁 cookie、原生页 Bearer"的凭据矩阵与 C-17 设备密钥的关系。

**R8 · FR-8.75（AMEND-22 修订）· 三端同源、可写；D76 废止**

- **修订后**：**Web 端与原生端同源、可写**——`browser_session` **不再**被全局强制只读；发送、上传、批准、删除在 Web 上可用（受 FR-8.7 / 8.8 的队列与审批规则约束）。原"顶部常驻只读横幅"仅出现在**显式只读会话**。
- **防护（必须随本条落地，缺一不得合并）**：①**CSRF**——写方法要求 `Origin` + `Sec-Fetch-Site` 同源校验，并校验与会话绑定的 **CSRF token**（double-submit）；cookie 用 `SameSite=Lax` 起步。②**XSS**——Markdown 仍禁原始 HTML（FR-8.29 不变）；Web 壳设 CSP 禁 `unsafe-inline` / `unsafe-eval`；管理面不回显用户 HTML。③**安全评审**——本条落地前须完成一轮针对 Web 写路径的独立安全评审（CSRF / XSS / 点击劫持 / 越权），评审结论作为合并门槛。
- **`READ_ONLY_SESSION` 收窄**：只用于**显式只读会话**（用户或管理员显式开启的只读模式 / 只读分享），**不再**由"cookie 凭据"隐式触发；错误码本身不变（C-04 不改）。
- **D76 废止**：D76「按凭据：Bearer 可写、cookie 一律只读」**已被 D100 废止**（决策 #14）。`READ_ONLY_SESSION` / `APPROVER_INVALID` 的后端拒绝逻辑保留，触发条件改为"显式只读会话"与"审批人身份不合规"。
- **判据**：Web（cookie 会话 + CSRF token）可发送消息、上传附件、批准审批，审计记录凭据类型为 `browser_session`；缺 CSRF token 的写请求 → `ORIGIN_MISMATCH` / `PERMISSION_DENIED`；显式只读会话下写请求 → `READ_ONLY_SESSION`；安全评审报告归档后才允许合并。
- **依赖**：**需 RFC-NNNN（待编号）· cookie 会话写路径的 CSRF 契约 + 审计凭据类型字段**；**方案层必须同步** `design.md` §7.1.3「按凭据判定」与 §7.10 只读矩阵（见 §8.22.6）。

## 11. 工程约定（开发组织）

### 11.1 并行结构

**先冻结接口，再并行**。并行度受依赖图约束，不能凭意愿拉满：

```
C0 验证 spike
   └─ C1 协议核心 ─ C2 传输/注册表 ─ C3 会话/队列/Loop
                          │
                          ├─ C4 Python SDK + echo ─────┐
                          │                            │
                          ├─ C5 审批/审计/配置页        │  ← 模块组前提：SDK v0.1 冻结
                          │                            ▼
                          │                   ┌── M1 fs
                          │                   ├── M2 shell
                          │                   ├── M3 web
                          │                   ├── M4 memory
                          │                   ├── M5 mcp-bridge
                          │                   └── M6 model
                          │
                          └─ U1 UI 骨架 + material
                                   ├─ U2 miuix 皮肤
                                   ├─ U3 glass 皮肤
                                   └─ U4 iOS
                                            │
                                            ▼
                                       F1 联调 + 安全 + 打包
```

| 并行组 | 成员 | 前提 |
|---|---|---|
| 第一批 | C4 / C5 / U1 | C3 完成，`schema/` 冻结 |
| **模块组** | M1–M6（6 个进程同时开发） | C4 的 SDK v0.1 冻结 |
| 皮肤组 | U2 / U3 | U1 的 `Skin` 接口冻结 |
| 收尾 | F1 | 全部完成 |

**模块组是全项目最干净的一段并行**：零共享代码、零目录冲突、零互相等待，唯一依赖是 SDK。

### 11.2 并行不冲突的三条硬约束

| 约束 | 做法 |
|---|---|
| **目录所有权** | 每个批次独占目录，跨目录只读。`schema/`、`protocol/v1/`、`modules/<name>/` 均由主线冻结后置为只读 |
| **契约先落文件** | 接口以 JSON Schema / `.proto` / Kotlin `interface` 文件形式先提交，代码后写 |
| **合并前全量验证** | 每个批次合并前必须跑全量测试 + 契约一致性检查，不做"局部绿"就合并 |

### 11.3 审查与返工

| 环节 | 谁做 | 输入 | 输出 |
|---|---|---|---|
| 开发 | 开发子代理（按批次） | 需求条目 + 接口契约 | 代码 + 自检记录 |
| 审查 | **新上下文审查子代理**（不继承开发过程） | 需求原文 + 方案 + `git diff` + 测试 | 「通过」或「问题清单」 |
| 返工 | **原开发子代理（resume）** | 问题清单 | 修复 + 说明 |
| 复验 | 原审查子代理（resume） | 修复后的 diff | 通过 / 再打回 |

**为什么返工回原代理而不是新开**：新代理要重建上下文，容易在修复 A 时改坏 B；原代理手里有实现意图。但审查必须换新上下文，否则会"护自己的代码"。

**返工上限 3 次**，超过则回到方案阶段重看设计——反复修补通常说明方案错了，不是代码错了。

### 11.4 批次交付物（每批必须有）

产品代码 · 测试 · 变更说明 · 验证证据（测试输出/截图/抓包） · 回滚方式 · 对应需求编号。
