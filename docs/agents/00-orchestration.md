# 编排手册（主线用）

> 你（编排者）**不写业务代码**。你的工作是：冻结契约、派活、收活、组织审查、裁决冲突、守住合并门禁。
> 一旦你开始改业务代码，就没有人能独立审查它了。

## 一、开工前的四件事

1. 确认 `docs/requirements.md` 与 `docs/design.md` 是最新版（当前 req v1.0+**AMEND-20**、design **v1.18**）。版本以 `docs/README.md` 的文档版本行为准。
2. 建仓库骨架：`core/ protocol/ schema/ sdk/ modules/ ui/ admin-ui/ deploy/ tests/ docs/rfc/`，只放 `.gitkeep` 与 `README`。
3. 把 `01-contracts.md` 的目录所有权表贴进 `CODEOWNERS`。
4. 建 `docs/status.md`（台账），字段见第九节。

## 三、派活模板（复制即用）

```text
你是 Vade Agent Runtime（简称 Vade）项目的开发子代理，代号 <AGENT_NAME>，负责批次 <BATCH>。

第一步：完整读这两个文件，不要跳读
- /workspace/vade/docs/agents/<BRIEF>.md   ← 你的任务书，以它为准
- /workspace/vade/docs/agents/01-contracts.md  ← 契约与目录所有权

第二步：读任务书「必读」一节列出的上游文档章节（只读列出的章节，不要通读全库）

第三步：按任务书的 T1…Tn 顺序实现，每完成一项跑该项的验收命令。
不要修改任务书之外的目录。发现契约有问题，停下来写 RFC，不要自行改契约。

交付时按任务书最后一节「交付格式」输出，必须包含：
1. 改动文件清单（含路径）
2. 每条验收命令的原始输出（不是"已通过"三个字）
3. 自检记录：哪些没做、为什么
4. 回滚方式（commit sha）
完成后不要自行宣布"可以合并"，等审查结论。
```

**给 agent 的上下文要克制**：只给路径，不给全文。让 agent 自己读，省的是你的上下文，不是它的。

## 四、审查派活

每个批次交付后，**新开两个上下文**（不得复用开发代理）：

```text
你是独立审查者，代号 <R1|R2>-<BATCH>，没有参与实现，也不继承开发过程。

材料：
- 需求：/workspace/vade/docs/requirements.md（只读与本批相关的 FR/AC）
- 方案：/workspace/vade/docs/design.md（只读与本批相关的章节）
- 任务书：/workspace/vade/docs/agents/<BRIEF>.md
- 改动：git diff <base>...<head>（含新增文件全文）
- 测试输出：<开发代理提供的原始输出>

按 /workspace/vade/docs/agents/70-R1-spec-review.md（或 71/72）执行。
只输出结论与问题清单，不要表扬，不要总结做对了什么。
```

| 批次类型 | 必跑审查 |
|---|---|
| C1 / C2 / C5a / C5b | R1 + R2 + **R3** |
| M1–M6 | R1 + R2 + **R3** |
| C3 / C3b / C3d / C4 / U1 | R1 + R2（C3b 追加一条：prompt 快照必须可复现） |

## 五、返工

1. 审查 `verdict = reject` → 把**问题清单原样**发给原开发代理：`resume <agent_id>` + 「按清单修复，逐条回复处理方式」。
2. 修复后由**原审查代理 resume** 复验，不新开。
3. 同一批第 3 次打回 → **停止返工**，编排者重看设计：反复修补通常说明方案错了。
4. 返工期间冻结该目录，其他 agent 不得改动；需要联动改契约的，先 RFC。

## 六、合并门禁（八条，缺一不合并）

## 八、冲突仲裁

| 情况 | 处理 |
|---|---|
| 两个 agent 都要改同一文件 | 按 `01-contracts.md` 的所有权判；所有者改，另一方提需求 |
| 契约不够用 | 停手写 RFC，编排者裁决；**不允许**先实现后补契约 |
| 需求歧义 | 编排者查 requirements 原文；原文没写 → 记录为「待定」并按最保守方案实现，标注假设 |
| 审查与开发争执 | 以需求原文为准；原文模糊时按「更安全 / 更不可逆代价更小」的一侧判 |
| 性能不达标 | 先加测量，再优化；不接受「感觉慢了」 |

|---|---|---|---|---|---|---|---|---|
| C0a | c0a-uniffi | 进行中 | — | — | — | — | 0 | |

## 十、什么时候停下来问人

只有这四类，其余自己判：

1. 需求冲突且两种解释都合理（例如「玻璃效果」是实现质感还是必须物理正确）。
2. 要突破安全边界（放宽白名单、允许模块反向调用、把私钥落盘）。
3. 返工第 3 次仍不过。
4. 要砍范围（例如 W-A 失败后是否接受 W-B 的第二份协议实现——这条已由 D21 预先授权，不必再问）。

## 十一、成本控制

| 手段 | 做法 |
|---|---|
| 不重复读 | 每个 agent 只读自己 brief 指定的章节 |
| 不重复写 | 契约文件只由所有者写，其他人引用路径 |
| 不空转 | 依赖未冻结就等待，不要"先写个大概" |
| 早失败 | C0 硬时限（C0a 4 天，C0b/C0c 3 天）；任何 spike 超过时限即出结论，不无限打磨 |
