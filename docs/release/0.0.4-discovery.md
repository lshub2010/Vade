# 0.0.4 — 发现模型缓存持久化设计

状态：实现记录（2026-11-25），对应 `model/discover` 的 0.0.3 契约，不新增 RPC 字段。

## 问题

0.0.3 的发现缓存只在 `ModelResolver` 进程内。用户在会话里选中 `builtin/<upstream-id>` 后，core 重启会丢失该条目；下一轮 `model.resolve` 返回 `model_unavailable`，用户必须重新刷新并重选。

## 存储

- 路径：`core.data_dir/models_discovered.json`
- 权限：`0600`；目录由 data_dir 管理
- 格式（version 2）：

```json
{"version":2,"endpoint_sha256":"<sha256(provider NUL base_url)>","discovered_at":"2026-11-25T00:00:00Z","ids":["qwen2.5-vl-72b"]}
```

只存上游 id、时间和端点摘要；**不存 API key、不存 base_url 明文、不推断能力**。

## 语义

- 只在 `model/discover` 成功时替换并原子写（tmp + `fsync` + `os.replace`）；失败、取消、超时都不覆盖旧文件。
- 启动时若文件存在、版本匹配且 `endpoint_sha256` 等于当前 `llm.provider + llm.base_url`，水合为 `priority=-1` 的发现条目；否则忽略（换网关/恢复旧 data_dir 不会把旧模型错误路由到新网关）。
- 配置的 `builtin/<llm.model>` 始终 `priority=0`，默认模型不会被水合改变。
- 仅 `can_discover()` 为真（builtin/openai/openai_compatible + 非空 base_url）时，缓存才进入 `catalog()`；`module`/`mock`/空 base_url 不暴露。
- 损坏 JSON、版本不符、字段类型不符：记录日志并忽略，不阻止 core 启动。

## 验收

- `core/tests/model/test_discovery_rpc.py`：成功发现、失败不覆盖、重启水合、端点变化不水合、损坏缓存、默认模型不变。
- `core/tests/...`：客户端设置页的 `not_discoverable` / 旧 core / 只读隐藏由 `ModelStateSeamPathTest` 覆盖；UI 渲染由客户端 CI 编译覆盖。
