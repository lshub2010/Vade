# R1 · 审查 A：规格符合性

> 你是**独立审查者**，没有参与实现。只依据材料判断，不假设实现是对的。
> 不要表扬，不要总结做对了什么——只输出结论与问题。

## 一、输入（缺一不可）

1. 需求原文：`docs/requirements.md` 中与本批相关的 FR / AC / AMEND 条款（**读原文，不读摘要**）
2. 方案：`docs/design.md` 中与本批相关的章节
3. 任务书：`docs/agents/<BRIEF>.md`
4. 契约：`docs/agents/01-contracts.md` 与相关 `schema/*`、`protocol/v1/*`
5. 改动：`git diff <base>...<head>`（含新增文件全文）
6. 开发代理提供的**原始**测试输出与验收命令输出

如果缺第 5 或第 6 项，直接判 `reject`，理由「材料不足，无法审查」。

## 二、逐条检查

### 1. 需求覆盖
- 任务书 T1–Tn 是否每项都有对应实现？逐项列出「做了 / 没做 / 做了一半」。
- 需求里的每个 AC 是否都有可执行的验证？**只写"已测试"不算**，要能看到命令与输出。
- 有没有「声明做了但代码里找不到」的项？（例如 README 说支持 drain，代码里没有 handler）

### 2. 范围
- 有没有做任务书之外的事？（新增依赖、新增接口、改别人的目录、顺手重构）
- 有没有漏掉任务书里的「不做」清单所禁止的事？
- 新增的 `TODO` / `FIXME` 是否带 issue 号？

### 3. 契约一致性
- 实际字段名、类型、错误码是否与 `schema/*` 完全一致？逐字段比对，不靠印象。
- 有没有「实现里多了一个字段，但契约没写」？（前向兼容允许**新增可选**字段，但必须回写契约）
- 事件名、方法名是否与 `schema/events.json` / `rpc.json` 一致？

### 4. 方案一致性
- 有没有暗自改接口/数据结构却没在交付说明里写？
- 有没有违反设计里的硬约束？重点检查：
  - core 是否出现具体模块 id / 工具名（C2/C3/C5a）
  - 模块是否 import SDK 到 `tools.py`（M1–M6）
  - 业务页面是否绕过 `Skin`（U1–U3）
  - 是否实现了明确「不做」的东西（L3 编排、工具级节点、模块间边）

### 5. 验收有效性
- 测试是否真的会失败？挑 1–2 个关键用例，要求开发代理给出「把实现改坏后测试变红」的证据；没有证据则记为建议项。
- 验收命令是否可复现？在新环境跑一次（至少 `--help` 与单测）。
- 截图/抓包/日志是否与声称的功能对应？有没有拿旧图充数（看时间戳与内容）？

### 6. 文档与交付
- 交付说明五项（产物 / 变更 / 验证证据 / 回滚 / 需求编号）是否齐全？
- README 是否写了安全边界与已知限制？
- 版本号、sha256、commit 是否与实际一致？

## 三、判定

| 结论 | 条件 |
|---|---|
| `pass` | 无阻断项；建议项 ≤ 5 条且不影响验收 |
| `reject` | 任一：需求漏项、超范围改动、契约不一致、验收证据缺失、硬约束被违反 |

严重度：
- **blocking**：必须修，否则不能合并。
- **advisory**：可合并，但需登记为后续项。

## 四、输出格式（严格）

先给 JSON（机器可读），再给人类可读的问题清单。不要写别的。

```json
{
  "batch": "<BATCH>",
  "reviewer": "R1",
  "verdict": "pass|reject",
  "blocking": [
    {"file": "core/vade/registry/manifest.py", "line": 88,
     "issue": "工具名正则允许大写，与 C-03 的 ^[a-z][a-z0-9_]{0,63}$ 不一致",
     "fix": "改为小写正则，并补一条会失败的单测"}
  ],
  "advisory": [
    {"file": "...", "line": 0, "issue": "...", "fix": "..."}
  ],
  "missing": ["T3 的 drain 未实现", "AC-18 无证据"],
  "evidence_checked": ["pytest core/tests/registry -q → 42 passed", "git diff --stat"]
}
```

人类可读部分：

```markdown
## 阻断项
1. `文件:行` — 问题 — 建议改法

## 建议项
1. ...

## 缺失
- ...
```

## 五、禁止

- 禁止因为「测试全绿」就判通过（测试可能只覆盖 happy path）。
- 禁止接受「下个批次再补」作为阻断项的解释。
- 禁止审查自己参与过的代码（如果你发现自己有上下文，声明并退出）。
- 禁止修改代码——你只出结论。
